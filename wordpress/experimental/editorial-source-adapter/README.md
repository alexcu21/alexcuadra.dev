# Adaptador de fuente — experimento local

Primera parte del adaptador de escritura. No es un plugin: no tiene cabecera instalable, hooks, abilities, migración ni paquete. No se incluye desde Read, Proposals o Changes Laboratory. `write_source` rechaza cualquier entorno distinto de local, origen distinto de `http://wordpress` o ausencia del opt-in explícito `AC_EDITORIAL_SOURCE_EXPERIMENT=true`. No se debe quitar este guard para instalarlo.

Contrato interno: recibe un documento de revisión ya autorizado por el futuro coordinador, un lector de snapshot fresco/bloqueado con la forma de `review_source`, un comprobador de esquema y una limpieza de caché WP/ACF. Requiere cuerpo/tagline con el mismo conjunto de campos antes/después. Nunca acepta título, slug, estado u otras claves de campo. Exige la referencia ACF original; diferencia fila ausente, cadena vacía y referencia presente. Comprueba versión/snapshot y esquema antes de escribir.

Solo cuerpo llama `wp_update_post`; solo tagline usa APIs ACF/meta. En ambos, el snapshot fresco posterior debe coincidir con lo previsto y conservar las demás filas/campos. Solo un cambio de cuerpo puede variar timestamps del post. Los retornos false de actualización de metadata no se interpretan automáticamente como fallo: la postcondición manda. Las cachés se limpian en finally incluso si falla una API. Al fallar cuerpo no continúa con metadata.

## Límite de este incremento

**No usar como ejecutor de escritura.** No valida aprobaciones/capacidades, no abre ni confirma transacciones, no registra eventos/recibos/intenciones, no difiere hooks LiteSpeed y no ejecuta compensaciones. Un fallo posterior al guardado exige rollback del futuro coordinador: este módulo no promete revertirlo. Los callbacks recibidos deben ser internos y fiables, nunca elegidos por un cliente. La validación y sanitización del documento de revisión preceden a esta capa. El lector debe rechazar metadatos duplicados y comprobar idioma/CPT/publicación y traducciones según el contrato de revisión.

La prueba `php tests/experimental/source-writer.php` usa dobles de las APIs WP y estado en memoria. Demuestra la frontera de llamadas y postcondiciones en39 comprobaciones, no comportamiento de hooks reales, SQL, ACF real, Polylang, concurrencia o purgas.

Siguiente incremento: intención durable por evento/Project, atómica con contenido/aprobación/recibo; consumidor solo de intenciones confirmadas y separación entre contenido aplicado y purga pendiente. Envolver exclusivamente la callback LiteSpeed auditada, restaurarla en finally y preservar operaciones ajenas. Probar rollback sin intención ejecutable, caída después de COMMIT, duplicados, fallo de purga y carreras en WordPress/SQL aislados antes de proponer un paquete real. El código experimental no debe llamar directamente al consumidor desde el guardado ni tratar una purga fallida como rollback de contenido.

## Segundo incremento: protocolo persistente SQLite

`effect-journal.php` ensaya el protocolo en SQLite real, exclusivamente local y con opt-in. No se integra con `write_source`: **una conexión SQLite y la conexión MariaDB de WordPress no comparten transacción**. Los callbacks de `record` solo pueden escribir fixtures con la misma conexión PDO recibida, sin DDL, COMMIT/ROLLBACK ni efectos externos. El coordinador de WordPress/MariaDB sigue pendiente; no se debe usar este journal para envolver APIs WP.

`record` guarda evento inmutable, contenido/aprobación de prueba, recibo e intención en una transacción. La clave de evento se valida con hash de entrada, Project y operación; un replay devuelve el recibo original sin reescribir ni depender del estado actual de la purga. No ejecuta purga dentro del guardado. Una recuperación usa otro evento/intención. Los recibos no se reescriben cuando cambia el estado del efecto.

Un consumidor separado reclama solo intenciones con evento confirmado mediante CAS, token aleatorio y lease30s. No mantiene transacción abierta durante la llamada externa. Los workers antiguos no pueden confirmar el lease de otro. El resultado aceptado significa aceptación por la API, no certifica todas las cachés invalidadas. Los demás resultados/excepciones quedan como reintento o incertidumbre, nunca como rollback del contenido. Backoff exponencial limitado300s; máximo8 intentos, después `attention` sin reintento automático. Las filas se conservan; no hay poda, cron ni consumidor registrado.

La ejecución externa es **al menos una vez**: si el proceso termina después de la invalidación y antes de guardar la confirmación, puede repetirse. Se usa una clave estable por evento/tipo/Project. La API futura debe admitir invalidación repetida usando el estado actual del Project. No se promete entrega exactamente una vez ni se aplica este protocolo a correos/notificaciones. Un lease no impide que una llamada externa muy lenta siga ejecutándose tras expirar: el token protege la confirmación en SQL, no bloquea la API externa. El reloj inyectado facilita el ensayo; una implementación distribuida debe usar un reloj de base de datos compartido.

Prueba: `php tests/experimental/effect-journal.php`. Usa una base temporal propia, dos conexiones, dos procesos que compiten por un lease y procesos que salen antes/después de una purga simulada. Limpia exclusivamente esa base sintética al terminar.54 comprobaciones correctas. No inicia Docker ni usa/redacta respaldos reales. La suite anterior del writer sigue con39 comprobaciones correctas.

Próximo paso concreto: portar el protocolo a la **misma conexión MariaDB** de la copia aislada, con esquema/índices/engine estrictos y admisión de backend de caché; implementar el envoltorio por operación para la callback LiteSpeed exacta y comprobar su restauración/preservación de llamadas ajenas. Solo entonces ensayar source writer+aprobación/recibo/intención con hooks WP reales, rollback y fallos de proceso. No instalar ni habilitar edición real por este resultado SQLite.

## Tercer incremento: WordPress/MariaDB y callback LiteSpeed reales

`mariadb-operation.php` incorpora un coordinador experimental que comparte `$wpdb` con las APIs WP/ACF. `record` exige que su conexión sea exactamente el `$wpdb` global usado por WordPress; consumidores sí pueden usar otra conexión. Conserva evento/recibo e intención junto con la escritura y la aprobación de fixture en InnoDB. El journal SQLite sigue separado como prueba de protocolo, no se usa para envolver WP. La instalación experimental es explícita y falla si las tablas ya existen; no migra ni repara. Se rechazan esquema propio alterado (columnas, índice primario, triggers y CHECK/FK), tablas seleccionadas no InnoDB, transacción externa y caché de objetos externo. Se exige WP7.1.3/local/origen exacto/opt-in; el caché nativo se identifica por clase y archivo core y ausencia de object-cache.php, incluso cuando el indicador WP devuelve null.

El envoltorio conserva la posición, identidad restaurada, prioridad y argumentos de `LiteSpeed\\Purge::purge_publish`10/3. Verifica el SHA256 exacto del archivo original7.9.2. Reemplaza temporalmente la función en su slot de WP_Hook (representación interna ligada a la versión); difiere únicamente transiciones publicadas del Project de esta operación. Otras transiciones siguen ejecutando el callback nativo. Restaura en finally y rechaza anidamiento/deriva. No desactiva plugins, elimina hooks completos ni cambia opciones de purga. No envuelve otras callbacks LiteSpeed; el perfil ensayado tiene sus opciones sintéticas por defecto.

El consumidor usa leases/token y reloj MariaDB, ocho intentos y reintentos acotados. No mantiene transacción durante el callback externo. Un evento sin recibo confirmado no es ejecutable. `requested` expresa invocación de la API, **no** entrega de invalidación en el hosting. Fallo de purga conserva el contenido ya confirmado y el recibo original. Como en SQLite, puede haber más de una invalidación ante caída tras invocarla; no debe usarse para notificaciones no idempotentes.

Prueba nueva: `PYTHONDONTWRITEBYTECODE=1 python3 tests/integration/wordpress-source-effects/run.py`. Crea un proyecto interno con imágenes cacheadas y datos sintéticos, sin puertos. Solo ACF6.8.10 y LiteSpeed7.9.2 se copian desde archivos verificados del respaldo; no importa SQL/config original ni activa otros plugins/MU/tema del sitio. Requiere8GiB libres, volúmenes tmpfs512+768MiB y detiene sus contenedores en finally. No hace SSH, pull, prune ni borra volúmenes o respaldos.58 comprobaciones reales correctas, además de39/54 de las suites anteriores.

**Todavía no es candidato instalable.** El callback de escritura es interno y fiable: no puede cambiar de conexión, confirmar transacciones, emitir efectos externos o escribir fuera de los campos autorizados. No hay registro MCP, autorizador real, aprobación consumible real, cuotas/retención del nuevo journal, revisión completa del perfil/hook/contexto o paquete/rollback operativo. El ensayo no incluye Polylang/Hostinger/MU/tema del hosting, HTTP, servidor LiteSpeed real ni muerte de procesos MariaDB; las muertes de procesos anteriores pertenecen al protocolo SQLite. El siguiente incremento debe comprobar HTTP y fallos de proceso en MariaDB con el perfil completo y los límites reales antes de plantear instalación o escritura pública.

## Cuarto incremento: HTTP y fallos reales de proceso MariaDB

El runner de integración ahora añade46 pruebas HTTP sobre Apache, con Basic/Application Passwords sintéticas y rechazo de anónimo/subscriber. Las rutas están en fixtures de test, no en este directorio ni en paquetes instalables. Se conserva el guard local/origen/opt-in del módulo y se reutilizan las mismas APIs/callback de purga.

SIGKILL antes de COMMIT revierte fuente completa/contador/intención. Después de COMMIT sobreviven fuente y efecto pendiente, y replay devuelve recibo sin ejecutar writer. Un consumidor muerto antes/después de la API deja un lease persistente: otro no lo toma hasta expirar; al retomar no escribe la fuente. Si la API ya se invocó, se repite la invalidación sin fingir exactly-once. Hay cabecera nativa en la respuesta HTTP de consumidor, no en fuente normal/rollback. Esto prueba Apache+API LiteSpeed local, no el caché del hosting.

El siguiente paso es el perfil completo, incluidos Polylang/MU/tema y lector de traducciones; no repetir estas pruebas de dos plugins como sustituto. Ver `docs/WORDPRESS_MCP_SOURCE_REMAINING.md`:1–2 iteraciones estimadas para cerrar el adaptador,4–6 en total para contrato/candidato e instalación autorizada, si no aparecen fallos nuevos.

## Recuperación operativa y sesión DB — cierre local

El contrato completo pasa94 controles, además de132 regresiones. prepareRecovery/recover requieren scope específico y aprobación nueva; conservan los recibos originales, consumen la reserva al límite y permiten renovar lo vencido solo con espacio adicional, sin borrar históricos. effectStatus admite apply o recover y sigue la última intención. Cuatro cortes reales de conexión incluyen apply, recover y la ejecución dentro de _do_query; mysqli/transaction/filtro final/lista cerrada impiden autoreplay sobre nueva sesión. Driver y filtro se restauran al salir. SQL directo arbitrario/drop-in DB no está admitido. Ante COMMIT incierto se reintenta/consulta la misma clave. [QA y límites](../../../docs/qa/MCP_OPERATING_RECOVERY_2026-10-23.md).

El runner admite AC_SOURCE_EFFECTS_REUSE_NETWORK únicamente para una red ac-source-effects propia, internal/bridge/local, con etiqueta Compose correspondiente y cero endpoints activos. Evita ampliar el pool agotado sin podar recursos. Imágenes cacheadas, DB/WP tmpfs, sin puertos, pulls o SQL/config real. No elimina redes/volúmenes. Almacenamiento del volumen35→33GiB durante el incremento (sin atribución exclusiva); registros privados160KiB, Docker/swap pueden usar disco.

Pendiente: migración/decoders/admisión estrictos, schemas/transporte MCP, export privado y candidato/preflight/reversión. No hay paquete instalable nuevo ni autorización de scopes/edición reales.
